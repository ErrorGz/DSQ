# “重氢分馏塔无法用于生产氢气”问题分析与解决方案

## 1. 结论摘要

1. 这条提示**不是蓝图导出器直接抛出的错误**，而是旧版计算器在 `Scripts/data.js` 的 `find(name, true)` 中，对配方进行“投入产出抵消”后，没有找到目标物品的净产物时抛出的通用错误。
2. 氢气的直接触发条件是：`settings_pf["氢"]` 指向了**重氢分馏塔配方**。该配方投入 1 个氢，产出 0.99 个氢和 0.01 个重氢；抵消后氢的净产出为 0，不能再作为“生产氢”的配方使用。
3. 在当前工作区的全新浏览器状态下，清空 `localStorage` 后，生成“粒子容器”“红矩阵”“液氢燃料棒”均正常，**不能仅凭版本升级稳定复现**。用户现场出现问题，优先检查保存的配方选择、数字下标是否错位，以及需求列表中是否还保留其他含氢物品。
4. 当前合并版本确实引入了上游 `f465a32` 的“两轮副产物抵扣”逻辑，但 `find()` 和这条警告本身早在 2024 年就已存在。新逻辑改变了计算路径，可能让旧的无效配方选择重新暴露；**直接根因仍是无效的氢气配方选择，而不是提示文案本身**。
5. 推荐修复顺序：
   - 先清除失效的配方存档，恢复使用；
   - 在 `find()` 中校验配方的净产出，无效时自动回退；
   - 在配方选择列表中过滤“不能净生产目标物品”的配方；
   - 长期将 `settings_pf` 的数字下标改为稳定配方标识，并增加迁移逻辑。

## 3. 错误触发链路

旧版计算器的调用链为：

```text
添加物品需求
  → addItem()
  → update_all()
  → expandDemand()
  → loadNumber(itemName, n)
  → find(itemName, true)
  → get(item)
  → 抵消投入与产出中的同名物品
  → 目标物品净产出为 0，进入警告和异常分支
```

关键位置：

- `Scripts/data.js` 的 `loadNumber()`：约第 6016 行；
- `Scripts/data.js` 的 `find()`：约第 5310 行；
- 警告与异常：约第 5357—5358 行；
- 两轮需求展开：约第 6233—6288 行。

运行时捕获到的典型堆栈为：

```text
Error: 配方错误！可能是因为该配方净输出为负。
    at get (Scripts/data.js:5358)
    at find (Scripts/data.js:5363)
    at loadNumber (Scripts/data.js:6036)
    at loadNumber (Scripts/data.js:6094)
    at expandDemand (Scripts/data.js:6270)
    at update_all (Scripts/data.js:6277)
```

失败调用参数为：

```js
{
  name: "氢",
  normalize_recipe: true,
  settings_pf: { 氢: 187 }
}
```

其中 `187` 是当前工作区中的分馏塔配方下标，**不是长期稳定的游戏配方 ID**。

## 4. 为什么分馏塔不能作为“生产氢”的配方

当前工作区共有 191 条配方。以下下标仅对当前数据数组有效：

| 物品 | 当前默认配方下标 | 生产设备 | 投入 | 产出 | 抵消后的净产物 |
|---|---:|---|---|---|---|
| 氢 | 31 | 轨道采集器（巨冰） | 无 | 氢 × 1 | 氢 × 1 |
| 重氢 | 30 | 轨道采集器（气态） | 无 | 重氢 × 1 | 重氢 × 1 |
| 氢（错误选择） | 187 | 分馏塔 | 氢 × 1 | 重氢 × 0.01、氢 × 0.99 | 重氢 × 0.01 |

分馏塔配方抵消过程：

```text
投入：氢 1
产出：氢 0.99 + 重氢 0.01
抵消：min(0.99, 1) = 0.99
结果：氢净产出 0，剩余重氢 0.01
```

所以分馏塔适合作为“生产重氢”的备选配方，不适合作为“生产氢”的配方。X 射线裂解制氢配方则不同：它产出 3 个氢、消耗 2 个氢，抵消后仍净产出 1 个氢，因此可以用于制氢。

问题的代码根源是：`getPfs("氢")` 只检查原始产物 `s[]` 中是否出现“氢”，没有检查抵消后是否仍有氢的净产出，所以分馏塔会出现在氢的备选配方中。一旦用户选择它，或旧存档数字下标错位到它，`find("氢", true)` 就会失败。

## 5. 复现与对照结果

### 5.1 全新状态

清空本站 `localStorage` 后：

| 需求 | `update_all()` | `getRecipe()` | 是否出现目标提示 |
|---|---|---|---|
| 粒子容器 | 正常 | 正常 | 否 |
| 红矩阵 | 正常 | 正常 | 否 |
| 液氢燃料棒 | 正常 | 正常 | 否 |

### 5.2 强制使用分馏塔制氢

设置：

```js
settings_pf["氢"] = 187;
```

| 需求 | 结果 |
|---|---|
| 红矩阵 | 稳定复现目标提示和异常 |
| 粒子容器 | 正常，不触发 |

改回：

```js
settings_pf["氢"] = 31;
```

红矩阵恢复为每 60 个红矩阵需求对应 120/min 氢需求，计算正常。

### 5.3 关于“粒子容器”

当前默认粒子容器配方（下标 62）为：

```text
电磁涡轮 × 2 + 铜块 × 2 + 石墨烯 × 2 → 粒子容器 × 1
```

默认展开没有正的氢净需求；石墨烯通过可燃冰生产时反而副产氢。60/min 粒子容器约产生 60/min 氢盈余。

因此，如果现场是**只保留粒子容器需求**仍出现该提示，建议重点检查：

1. `xqs` 中是否还残留红矩阵、燃料棒、等离子胶囊等其他需求；
2. 是否使用了非默认的石墨烯或其他备选配方；
3. 控制台堆栈是否确实来自 `loadNumber("氢", ...)`；
4. `settings_pf` 的实际内容，而不是只看界面当前选中项。

## 6. 为什么表现为“上一个版本正常，当前版本异常”

需要区分三层原因：

### 6.1 直接原因

`settings_pf["氢"]` 无效，指向了抵消后不产出氢的配方，或者数字下标因数据数组变化而错位。

### 6.2 版本变化

当前合并版本引入了两轮副产物抵扣：

```text
第一轮：不抵扣，统计副产盈余
第二轮：使用副产额度，重新展开需求
```

这改变了 `loadNumber()` 的调用次数和顺序，也让旧的净配平路径再次成为关键路径。但两轮抵扣**不会自动把氢配方改成分馏塔**，不能把它单独认定为直接根因。

### 6.3 存档设计缺陷

`settings_pf` 保存的是 `data` 数组的数字下标：

```js
settings_pf[name] = parseInt(value);
```

而 `find()` 直接读取：

```js
return get(data[parseInt(pf)]);
```

数据数组一旦插入、删除或重排配方，旧下标就会指向另一条配方。当前代码只在注释中提醒“数据改变时有可能需要重置配方”，没有稳定标识和迁移校验。

综合判断：**新版本改变了计算流程，并继续沿用脆弱的数字下标存档；在已有失效配方选择时，旧问题会重新暴露。** 上游同样如此，是因为上游也使用这套实现。

## 7. 临时恢复办法

### 7.1 只重置氢气配方

打开页面开发者工具，在 Console 执行：

```js
delete settings_pf["氢"];
saveSettingPf();
update_all();
```

然后重新添加需求。

### 7.2 重置全部配方选择

如果还有其他物品的备选配方可能错位，执行：

```js
settings_pf = {};
saveSettingPf();
location.reload();
```

这比直接清空全部 `localStorage` 更安全，不会顺带清除参数设置、设备速度和项目存档。

### 7.3 检查现场状态

```js
console.log("配方存档：", settings_pf);
console.log("当前需求：", xqs.map(function (x) { return x.item.name; }));
console.log("氢配方：", find("氢", true));
console.log("重氢配方：", find("重氢", true));
```

预期：

- 氢配方机器应为“轨道采集器（巨冰）”；
- 重氢配方机器应为“轨道采集器（气态）”或用户主动选择的分馏塔；
- 不应出现 `settings_pf["氢"]` 指向分馏塔的情况。

## 8. 永久修复方案

### 8.1 最小安全补丁

目标：不改变现有配方数据，先阻止无效存档导致崩溃。

#### 1. `find()` 内部只判断“是否净产出目标物品”

将 `get(item)` 在找不到目标净产物时的行为从“警告并抛错”改为“返回 `null`”。

#### 2. 校验保存的配方，无效时自动回退

推荐逻辑：

```js
function find(name, normalize_recipe) {
  function get(item) {
    var o = $.extend(true, {}, item);

    if (normalize_recipe) {
      // 保留原有默认值补齐和投入产出抵消逻辑
    }

    for (var j = 0; j < o.s.length; j++) {
      if (o.s[j].name == name) {
        $.extend(o, o.s[j]);
        return o;
      }
    }

    return null;
  }

  var pf = settings_pf[name];
  if (pf !== undefined && pf !== null) {
    var selected = data[parseInt(pf, 10)];
    var result = selected && get(selected);
    if (result) return result;

    // 下标越界、配方错位或净产出为 0：删除失效存档并回退
    delete settings_pf[name];
  }

  for (var i = 0; i < data.length; i++) {
    var item = data[i];
    for (var j = 0; j < item.s.length; j++) {
      if (item.s[j].name == name) {
        var candidate = get(item);
        if (candidate) return candidate;
      }
    }
  }

  return null;
}
```

#### 3. 调用方处理 `null`

`loadNumber()` 应增加明确判断：

```js
var item = find(itemName, true);
if (!item) {
  throw new Error("没有可用于生产“" + itemName + "”的有效配方。");
}
```

不要让 `getValue()`、`item.q` 等后续代码继续访问空对象。

#### 4. 过滤备选配方列表

`getPfs(name)` 不应只检查原始 `s[]`，还应检查抵消后是否仍有 `name` 的净产出。过滤后：

- 氢的备选配方中不再出现分馏塔；
- 重氢的备选配方中仍可保留分馏塔；
- X 射线裂解制氢仍可正常出现；
- 重整精炼配方不会被误列为制氢配方。

#### 5. 移除硬编码提示

不要在 `find()` 中无论查找什么物品都提示“重氢分馏塔无法用于生产氢气”。错误信息应包含：

- 目标物品；
- 选中的配方；
- 生产设备；
- 抵消后的净产物；
- 配方下标或稳定标识。

### 8.2 稳定配方标识与迁移

长期应停止用数组下标作为存档值。

推荐为每条配方生成稳定 key：

```js
function getRecipeKey(item) {
  if (item.gameId) return "game:" + item.gameId;

  var inputs = item.q.map(function (q) {
    return q.name + "x" + (q.n || 1);
  }).sort().join("+");

  var outputs = item.s.map(function (s) {
    return s.name + "x" + (s.n || 1);
  }).sort().join("+");

  return item.mName + ":" + inputs + ">" + outputs;
}
```

然后：

1. 新存档保存 `getRecipeKey(recipe)`，而不是数字下标；
2. 读取存档时按 key 查找配方；
3. 对旧数字下标做一次迁移，但迁移前必须验证该配方确实能净产出目标物品；
4. 验证失败时删除对应旧存档并回退默认配方；
5. 数据数组新增配方时，不再影响已有存档。

### 8.3 副产物抵扣的数值容差

当前 `loadNumber()` 使用：

```js
if (n === 0) { ... }
```

浮点抵扣可能留下极小残差，建议先归一化：

```js
if (Math.abs(n) <= 1e-9) n = 0;
```

这不是本次氢气异常的直接原因，但能避免把机器误差当成新的微小需求，减少后续递归和配方切换问题。

### 8.4 参考新简易版计算器

`dsqnew/calc.js` 已采用更合理的模型：

- `prepare()` 先抵消投入产出；
- 只把 `out` 中仍有净产物的物品加入 `PRODUCERS`；
- 因此分馏塔只会作为重氢生产者，不会作为氢生产者。

旧版 `Scripts/data.js` 可以复用这一思路，避免两套计算逻辑对“是否能生产某物品”的判断不一致。

## 11. 最终建议

- **立即恢复**：清除 `settings_pf` 中的失效选择，不必清空全部站点数据。
- **第一轮修复**：在 `find()` 中验证净产出并自动回退，同时过滤 `getPfs()`。这是防止崩溃的最小改动。
- **第二轮修复**：将配方存档从数字下标改为稳定 key，并加入旧存档迁移。
- **上游协作**：可向上游提交 issue 或 PR，重点描述“数字下标存档 + 未过滤净产出为 0 的备选配方”，而不是只描述提示文案。

文档结论基于当前工作区源码、Git 历史、上游当前源码以及全新浏览器状态下的运行时对照。
